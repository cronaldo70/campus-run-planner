# 校园实跑路线规划 · 避障版

在 Windows 双击项目根目录的 `启动校园跑.bat`（唯一入口），打开「校园实跑路线规划 · 开始跑步」。它已经建好 `work\.venv`、装好依赖；想跳过来直接看这一版，在根目录执行 `启动校园跑.bat` 即可，也可以在界面里点「工具 → 打开旧版规划器」切到另一个前端。离线路线规划无需连接手机。

## 怎么用

1. 手机用 USB 连接 Windows，解锁并打开乐跑地图，完整显示打卡点列表。点「读取手机打卡点（自动规划）」。这一入口使用 Apple Devices、现有的 pymobiledevice3 截图功能和 Windows 中文 OCR，支持一到两个打卡点。每次读取都会刷新名单。
2. 起点不用手输，也**不用再切指南针**（iOS 16 起苹果指南针只显示方位角和城市，不再给经纬度，实测 iOS 27.2 只显示「106° 东 / 安徽省合肥市」）。保持在同一张打卡点列表页，直接点「读取真实起点（自动）」：程序会先清掉上一次模拟跑留下的假位置、等 3 秒让定位落回手机真实所在，再读每一行「距你 N 米」，把它当成到该打卡点的距离，反解出手机位置。
   - 两个打卡点时是两圆相交的镜像双解，程序按「是否在校区边界内、离可跑路段多远、是否落在水面或建筑里、离上次起点多远」打分，选合理的一处；屏幕上还会写出另一个候选坐标，觉得不对就在地图上点一下覆盖。
   - 三个及以上打卡点时会做最小二乘，残差直接写进提示行。
   - 底图里「文典阁西门」「篮球场南门」这类入口只是估算位置，读数对不上几十米属正常，提示行会写残差；起点仍然会被吸到最近的可跑路段上。
3. 能匹配的打卡点会自动标到地图上，「蕙园」「文典阁西门」「篮球场南门」使用底图估算入口。点左边的打卡点按钮可更正位置，未匹配的点也在这里手动标记。标点离路较远时，短虚线标出吸附到的道路位置，虚线长度不计入路线。
4. 终点默认由规划器按最低里程安排。路线达到门槛后，点右下角「模拟跑这条路线（手机不用动）」：先在手机上点「开始乐跑」，回到电脑点「开始模拟跑」，倒计时 5 秒后按设定的配速把路线回放到手机，步道乐跑会把它当成真实跑步记录，跑完自动停止并恢复真实定位。目标配速默认 4:40 / 公里，2.5 公里约 11 分 40 秒。原来那个「开始跑步」（只会在电脑上走一个秒表、手机什么都不发生）已经从界面上删掉，只保留会真的让手机记录的「模拟跑这条路线」。
   - 规划长度会按 1.02 倍 + 25 米留余量：转角圆化会内切掉 1–2 %，而 App 量的是回放出来的轨迹。填 2.5 公里时规划约 2.58 公里、实际轨迹约 2.54 公里，才能稳稳过线；窗口里会同时显示「实际 X 公里」，万一短了会标红提示。
5. 遇到临时施工或封路时，选「封闭 / 恢复一段路」，放大地图后点对应路段。红线表示本次打开窗口期间封闭的路段，再点可恢复。
6. 「仅限校区内」默认开启，使用 OpenStreetMap 的磬苑校区边界。若实际允许跑到校外，可取消勾选查看附近步行路线。所有模式都应用水域、建筑和通行限制。

## 模拟跑的前提

- 只连一台 iPhone 并保持解锁；同一时间只能有一个程序占用定位隧道，另一个规划器或后台脚本开着会报「A userspace tunnel is already active」。
- 电脑需要 `pymobiledevice3`（项目根 `requirements.txt`，`work\.venv` 已装好），手机要开开发者模式（iOS 17+）。
- 模拟跑期间手机屏幕上仍显示真实蓝点以外的位置，属于正常现象；跑完或点「停止并恢复真实定位」就回到真实定位。中途关窗口也会自动停止。
- 轨迹会写一份 GPX 到 `outputs/real-run-planner/generated/`，可以用 `outputs/run-planner/check_gpx.py` 复核点数与里程。

## 读不到起点时

| 现象 | 原因与处理 |
| --- | --- |
| 「屏幕上的距离是 … 公里」 | 手机还停在上一轮模拟跑的位置上（距离变成几公里）。先点「停止并恢复真实定位」，等蓝点回到身边再读。 |
| 「能对上的打卡点不足两个」 | 当天只有一个打卡点，或者名单里的名字底图里确实没有（写在 `generated/unresolved.txt` 里）。在地图上点选起点，其余照常规划。 |
| 「路网里这几个打卡点只有近似位置，距离对不上 N 米」 | 底图里「文典阁西门」这类点位只是楼门估算，残差几十米是正常的；核对「起」标记，必要时手动覆盖。 |
| 「A userspace tunnel is already active」/「请只连接并解锁一台 iPhone」 | 同时开了两个规划器或后台脚本。关掉多余的窗口再试。 |

## 路线为什么不再是折线

地图上原来是一条一段一段的折线，因为画出来的就是 OSM 的原始路网顶点（中位段长 18.8 米，最长 933 米），拐弯是硬角，补里程的尾巴又是「沿一条路跑到头再原路折回」的 U 形，视觉上像机器人轨迹。现在分三层处理：

- **圆角**：每个拐点用 12 米的二次贝塞尔圆角替换硬角，跟真人贴着路缘拐弯一致；画布上的线和手机回放的轨迹用同一份点，看到什么就是跑什么。
- **掉头**：到打卡点门口必须原路折返的地方（打卡点常在支路尽头），把 180° 尖刺换成 3 米半径的小半圆，真人也是这么转身的；补里程的尾巴改成环形——出去走一条路、回来换另一条路，不再原路折回。实测 A→B→A 折返 3 处 → 0 处。
- **采样**：按 1.5 米间距重采样，再叠加三层波长的横向偏移（±2 米，模拟 GPS 抖动）。

同一路线实测（起点文典阁西门、打卡点篮球场南门 + 磬苑广场、最低 2.5 公里）：最大转角 180° → 48°，>45° 的转折 20 处 → 2 处，离道路中心线中位 0 米 / 99% 分位 5.4 米 / 最远 6 米（就是路宽），轨迹 2580 米、11 分 37 秒、配速 4:19–4:58。

## 拿真实记录对过参数

对照你之前两张真记录：龙河校区 2.50 公里 / 12 分 26 秒 / 平均 4'58"、2 个打卡；磬苑校区 3.39 公里 / 20 分 58 秒 / 平均 6'11"、2 个打卡；详情页的分段是 **第 1 公里 5'09" · 第 2 公里 4'27" · 最后不足一公里 5'46"**，最快 4'27"。也就是说真人记录不是匀速：

- 起跑头几百米明显慢（jog start），中段越跑越快，最后一小段落回慢速。生成器现在按这个形状走：`pace_profile(..., warmup=22, push=0.09, cooldown=34)`，再把整体归一化回目标配速，所以平均配速仍然精确。
- 目标配速默认从 4:40 改成 **5:00**，跟你那张 2.50 公里 / 4'58" 的有效记录一致；2.5 公里约 12 分 50 秒。跑 2.57 公里时典型分段是 5:02 / 4:50 / 5:14，和你 5'09 / 4'27 / 5'46 是同一种「先慢、中间快、最后放」的形状。
- 模拟跑窗口跑完会把分段直接打出来（`第 1 公里 5:02 · 第 2 公里 4:50 · 最后 0.57 公里 5:14`），可以跟 App 详情页逐公里对照。
- 真记录里的轨迹本来就有尖角和折返（第二张图终点附近那个 V 形），所以现在只把「原路折回的长尾巴」换成环形，掉头处留 3 米小半圆，不再强行拉直。

## 怎么判断避障

规划只沿图上已连通的道路中心线。穿越已测绘水面、河道或建筑的路段会从候选中剔除。带步行权限的已标注桥梁可跨水域，仍受校区、围栏和通行限制。灰色虚线是已避开的路段。现有底图中的可用桥段都在校园边界以外，因此默认校区内模式可能不会显示蓝色桥段。路线不通时请改选入口或现场可通行的道路。

底图准不准可以直接量：把生成的轨迹逐点投到路网中心线上，偏离中位 **0 米**、99% 分位 **5.4 米**、最远 6 米——也就是一直压在路面宽度之内。步道乐跑自己画线时会再做一次平滑和抽稀，加上手机定位本身的抖动，App 里的线看起来会比我们的更「飘」一点；如果 App 里明显跑到小区或校外，先看拍下来的 GPX 有没有那段，再看是不是 App 的平滑把拐角抹圆了。施工、开放时段和真实路况仍需现场确认，运动记录以手机 App 为准。

本机通过了水面绕行、桥梁通行、建筑与围栏拦截、校园边界、手动封路和撤销的离线测试，也用磬苑校区路网验证了蕙园附近至文典阁附近的连通路线。截图中的具体桥段尚未做现场核验。

## 打卡点名字为什么都能认出来（570 个）

原来 `campus.json` 只有 15 个手工标签（笃行北楼、文典阁西门、篮球场南门…），步道乐跑换一批打卡点就有一半认不出，比如「人文楼东侧」在表里根本没有。现在改成从 `work/campus.osm` 全量生成：

- 取 76 个校区内的**带名字面状地物**（教学楼、宿舍园、餐厅、体育场地、门、医院…），每个产出「本体 + 东侧/西侧/南侧/北侧 + 东门/西门/南门/北门」共 9 个名字，一共 **570 个标签**（新增 555 个）。
- 每个点都吸附到最近的可走路段，且不会落在建筑或水面里（`nearest_clear`），所以打卡点一定跑得到。
- 名字差一点也能对上：先精确匹配，再去掉方向后缀（`人文楼东侧` → `人文楼`），再试补「楼/馆/园/场/中心/大楼」，最后按相似度兜底（OCR 把「楼」认成「棧」也能中）。实在对不上的名字写进 `generated/unresolved.txt` 备查。
- 地图上只画**当前路线附近 70 米内**的名字（没有路线时只画十几个地标），否则 570 个名字会把地图糊死。

重建标签表：`python work/build_labels.py`（会先备份成 `campus.json.bak`）。

## 路线为什么不再穿湖

穿湖不是寻路的锅：路网里跨水的边早就被判成「水域」剔除了（可走边中点为水面的 = 0）。真正的原因是**平滑**——`round_corners` 转弯内切最多 12 米、`wobble` 横向抖动原先 ±2 米，而湖边最近的可走边离水面只有 2.9 米，一抖就进水了。现在两道保险：

- `WOBBLE` 从 2.0 降到 **1.5 米**；
- 轨迹生成后加 `snap_clear()`：逐点检查是否落在水面或建筑里，落在里面就投影回最近的路面（离路超过 30 米才放弃）。

实测四条真实规划路线（文典阁西门→人文楼东侧+行政楼、→磬苑体育馆+蕙园3栋、人文楼东侧→艺术楼+主体育场、校医院→行政楼+磬苑体育馆）：轨迹点 992–1322 个，**水域点 0、建筑点 0**，画布上那条圆角后的线同样 0。

## 为什么以前看起来在草地上斜穿

这不是轨迹抖，也不是底图偏——是**两边地图画的不是同一批线**。OSM 里除了车行道，还有大量校内人行小径（`highway=footway/path`）：绿化带里抄近道的斜线、楼与楼之间的连廊、湖边的步道。这类线 OSM 有、**步道乐跑用的高德底图不画**，于是轨迹贴着一条小径走，手机上看就是一条直线劈过草坪。

实测那次录制（`real-run-20261114-152125.gpx`，2.56 公里）：4% 的点落在 `path` 上，而那段正好是从九龙路拐进绿化带的一百多米对角线，与手机截图里绿色斜线重合。

现在给 `path` 加权：

- 寻路成本里 `path` 的每米长度按 **6 倍**计（`PATH_PENALTY`），只有绕路超过 6 倍才会用小径；
- 标点吸附时小径要比大路近一倍才优先（`PATH_NEAREST = 2.0`）；
- 返回的里程仍是真实地面距离，不受权重影响。

五条纯环线（西门北侧、文典阁西门、校医院、人文楼东侧、磬苑体育馆，各 2.5 公里）实测：`path` 占比 **0–0.3%**。余下的一点是打卡点门口的支路——`行政楼` 这类楼只能走楼前小径进去，出来再原路返回，那几百米无法避开，但那是「走到楼门口打卡」，不是横穿草坪。

## 源码与数据

- `real_run.py` 提供地图、标点和临时封路界面。
- `real_position.py` 从打卡点列表的「距你 N 米」反解起点（两圆相交、最小二乘、镜像解打分）。可单独跑 `python real_position.py 截图.png` 复核。
- `real_run_sim.py` 把画好的路线变成按配速推进的时间戳轨迹，并驱动手机定位回放；同时提供「是否在校区、离路多远、是否在水面建筑里」的判定。
- `read_checkpoints.py` 复用原有的 USB 截图和 Windows OCR 模块，读取可见打卡点名单。
- `pedestrian_routes.py` 校验路段几何和通行条件，并在剩余连通路网上寻路。
- `build_map.py` 负责把 OSM 源数据转换为 `campus.json`。可从工作区根目录运行 `python outputs/real-run-planner/build_map.py work/campus.osm outputs/real-run-planner/campus.json` 重建。
